## 一句话结论

ThunderAgent 的核心判断是：agentic inference 的吞吐瓶颈来自 runtime 缺少跨多轮 LLM 调用、工具执行和 KV cache 生命周期的统一对象；它把一条 agent workflow 抽象成 LLM Program，并用 program-aware scheduler 同时管理 GPU KV cache、tool environment 和跨节点 placement，在高并发 serving 与 RL rollout 中降低 re-prefill、闲置缓存和工具资源泄漏。

## 阅读目标与判断边界

本笔记关注：

1. ThunderAgent 如何把多轮 agent workflow 抽象成可调度对象。
2. program-aware scheduler 如何在 KV 复用、重算和跨节点负载之间做权衡。
3. 论文实验对 online agentic serving 与 RL rollout infrastructure 的启发。

## 论文脉络

### 1. 研究问题、背景和价值

agentic workflow 的实际运行形态是多轮循环：LLM 生成动作，外部工具执行，工具结果再进入下一轮上下文。传统 serving engine 看到的是一批独立 chat completion 请求；agent controller / Kubernetes 一侧看到的是工具环境、Docker、端口和文件系统资源。两侧都缺少完整 workflow 状态，导致三类系统损耗：

1. KV cache thrashing：工具调用期间，当前 program 的 KV cache 可能被别的 decode request 挤出；工具返回后又要对完整历史重新 prefill。论文在 Figure 1 中报告 re-prefill 可使平均端到端 latency 增加到最高 $7.14\times$。
2. 跨节点内存不均衡：session-aware routing 会把同一 workflow 绑定到固定节点以保 KV 复用；当不同 program 的上下文长度和工具等待时间高度异质时，有的节点 HBM 饱和，有的节点空闲。
3. tool lifecycle obliviousness：LLM engine 不知道工具环境生命周期，工具 orchestrator 不知道 LLM 程序何时结束，Docker sandbox、端口、磁盘文件和环境初始化时间会在长时间 rollout 中累积。

这篇论文的价值在于把 “agentic workflow 是 serving runtime 的一等对象” 具体化为系统 API、调度状态、cost model 和可运行实现。

### 2. 已有解决方案与不足

论文主要对照三类方案：

- vLLM / SGLang 这类 request-level engine：擅长单轮请求的 batching、prefill/decode 调度和 KV block 管理，但缺少 agent workflow 的 phase、tool wait 和 termination signal。
- KV-aware routing / session pinning：可以提升同一 session 的 KV 命中率，但容易把负载集中到少数节点；长上下文、多工具和异步返回会放大 imbalance。
- Continuum / tiered KV cache / offloading：试图用 TTL、工具时长预测或 CPU/NVMe cache 降低 KV 丢失成本；在高频 agent context switching 下，offload/prefetch 带宽和 stale cache 占用会成为新瓶颈。

ThunderAgent 的设计方向是让调度器直接看到 program 粒度的状态，减少对请求历史、session id 或 tool timeout 的间接推断。

### 3. 作者可能的思考路径

作者从 agent workload 的生命周期出发：一次 agent 任务跨多个 LLM request 和多个 tool execution，真正需要优化的是整条 program 在 GPU 与工具资源上的 space-time cost。若 runtime 只优化当前 request 的吞吐，它可能保存了短期内不会返回的 acting program KV，也可能驱逐了即将继续 decode 的 reasoning program KV。于是需要一个状态对象记录：

- 当前 program 属于 reasoning 还是 acting；
- context token count 对应多少 KV footprint；
- program 当前绑定到哪一个 backend；
- 工具资源是否存在、是否需要预热、何时可回收；
- program 是否 active、paused 或 terminated。

这样 scheduler 可以在高并发下做主动 pause / restore，避免只在 backend 触发被动 KV eviction 后才反应。

### 4. 核心假设或切入点

ThunderAgent 的核心切入点是 LLM Program：

$$
P=\langle \mathit{ID},c,\mathcal{T},\mathcal{L},\tau,s\rangle
$$

其中 $\mathit{ID}$ 是 program id，$c$ 是上下文 token 数和 KV footprint，$\mathcal{T}$ 是工具环境集合，$\mathcal{L}$ 是 backend placement，$\tau$ 是 phase（Reasoning $\mathbf{R}$ 或 Acting $\mathbf{A}$），$s$ 是 status（Active、Paused、Terminated）。

这个抽象使得 runtime 可以用显式状态做三类决策：

1. acting program 长时间等待工具时，KV cache 的有效优先级随等待时间下降。
2. reasoning program 即将继续 decode 时，优先保留或恢复其 KV。
3. paused program 的 KV 已经释放后，可以放入全局队列并在任意空闲节点恢复，降低 session pinning 造成的 imbalance。

### 5. 方法 / 系统 / 理论框架

ThunderAgent 由 program-aware scheduler 和 tool resource manager 组成。

**Cost model.** 论文用 Space-Time Product 衡量资源占用：

$$
\mathrm{Cost}_x=\int_0^{t_x}M_x(t)\,dt
$$

总成本分解为：

$$
\mathrm{Cost}_{\mathrm{total}}\approx
\mathrm{Cost}_{\mathrm{decode}}+
\mathrm{Cost}_{\mathrm{prefill}}+
\mathrm{Cost}_{\mathrm{recompute}}+
\mathrm{Cost}_{\mathrm{unused}}+
\mathrm{Cost}_{\mathrm{caching}}
$$

其中 decode / prefill 是有效工作，recompute、unused、caching 是开销项。调度目标是减少重算和闲置缓存，同时保持 decode/prefill 设备利用率。

**Pause / restore.** restore 把 paused program 绑定到某个 backend 并激活：

$$
P\leftarrow\langle \mathit{ID},c,\mathcal{T},\mathcal{L}',\tau,\mathrm{Active}\rangle
$$

pause 解绑 backend 并释放 KV：

$$
P\leftarrow\langle \mathit{ID},c,\mathcal{T},\varnothing,\tau,\mathrm{Paused}\rangle
$$

**周期性 thrashing detection.** 基础判断是当前 backend 的 KV 需求超过容量：

$$
C_{\mathrm{total}}<\sum_{p\in\mathcal{L}}c_p
$$

若超过容量，scheduler 需要释放：

$$
\Delta C=\sum_{p\in\mathcal{L}}c_p-\lambda_{\max}C_{\mathrm{total}}
$$

恢复阈值为：

$$
\sum_{p\in\mathcal{L}}c_p < \lambda_{\min}C_{\mathrm{total}}
$$

论文实现中 $\lambda_{\max}$ 和 $\lambda_{\min}$ 均设为 $1$，并用 shared prompt 预留 buffer。

**Acting program 的时间衰减。** 工具执行时长不稳定，ThunderAgent 对 acting program 的有效 KV footprint 加上时间衰减：

$$
C_{\mathrm{total}}
<
\sum_{p\in\mathcal{L},\tau=\mathbf{R}}c_p
+
\sum_{q\in\mathcal{L},\tau=\mathbf{A}}c_q f(t_q)
$$

$t_q$ 是当前 step 的 tool execution time。附录定理在不可预测工具返回时间与边界条件下推导出连续时间指数衰减或离散 tick 几何衰减；实现采用 $f(t)=2^{-t}$，检测周期 $\Delta t=5$。

这个式子描述调度器的有效保留权重，实际 KV footprint 仍由 $c_q$ 决定，历史已经占用的 HBM 也不构成当前决策成本。更准确地说，$c_q f(t_q)$ 是调度器给 acting program 的有效保留权重：reasoning program 正在 decode / prefill，按完整 $c_p$ 计入容量压力；acting program 正在等待工具，暂时不贡献 GPU 有效工作，因此其保留优先级随等待时间下降。当有效需求超过 $C_{\mathrm{total}}$ 时，scheduler 更倾向释放等待较久的 acting KV，把 HBM 留给正在 reasoning 的 program。

因此，时间衰减应理解为 KV reservation aging policy。它的当前决策依据仍应是未来边际收益与未来机会成本：继续保留 KV 可以省去未来 re-prefill / recompute，但继续占用 HBM 会挤出其他 reasoning program。Elapsed acting time 本身并不等同于剩余工具时间预测；在严格 memoryless 工具时长下，已等待时间不会改变剩余时间分布。论文附录的指数 / 几何衰减推导实际依赖两个额外假设：衰减只依赖 elapsed time，并满足 time-homogeneous 相对衰减 $f(t+\Delta)=f(t)f(\Delta)$，再加上 $f(0)=1,\lim_{t\to\infty}f(t)=0$ 的边界条件。

**Shortest-first eviction.** 论文把重算 STP 写成与上下文长度平方成比例：

$$
\mathrm{Cost}_{\mathrm{recompute}}
=
\int_0^{t_{\mathrm{recompute}}}c_i(t)\,dt
\propto c_i^2
$$

释放容量时的优化问题是：

$$
\min_S\sum_{i\in S}c_i^2
\quad\text{s.t.}\quad
\sum_{i\in S}c_i\ge\Delta C
$$

凸性来自 STP 口径：重算时间近似随上下文长度 $c_i$ 线性增加，重算过程中已恢复的 KV footprint 也从 0 增长到 $c_i$，因此“平均 footprint $\times$ 重算时间”近似与 $c_i^2$ 成比例。由于长上下文重算成本是凸的，调度器优先 pause 短上下文 program。具体打分为：

$$
S_{\mathrm{restore}}(P)=\frac{1}{c_P}+\mathbb{I}(\tau=\mathbf{R})
$$

$$
S_{\mathrm{pause}}(P)=\frac{1}{c_P}+\mathbb{I}(\tau=\mathbf{A})
$$

这等价于先按 phase 决定大方向：pause acting 优先、restore reasoning 优先；同一类内再做 shortest-first。

**全局 program-aware waiting queue.** paused program 的 KV 已释放后，恢复位置不再受原 backend 限制，可以进入全局队列等待任意节点容量。论文给出一个 unused cost 上界：

$$
C_{\mathrm{unused}}<c_{\min}\Delta t
$$

这个队列把 “保持同一 instance KV 亲和” 改成 “在值得保留时保留，在释放后可迁移”，是 ThunderAgent 相比简单 session pinning 的关键差异。

**Tool resource management.** 工具侧有两项机制：

- hook-based garbage collection：program 进入 Terminated 时，回收 sandbox、socket、磁盘和计算资源。
- asynchronous environment preparation：全局队列预测某个 program 即将 restore 时，提前准备工具环境，把环境初始化隐藏在 GPU 等待阶段。

### 6. 结论链条

论文的结论链条可以概括为：

1. agent workflow 有 persistent KV state 与 persistent tool state。
2. request-level serving 会把这些状态切碎，造成 re-prefill、HBM imbalance 和 tool resource leakage。
3. LLM Program 把 workflow id、phase、tokens、placement、tool resources 和 status 合成统一调度对象。
4. 基于 STP 的 scheduler 可以在 acting / reasoning、短 / 长上下文、local / global restore 之间做可解释 trade-off。
5. 这个抽象可以作为 middleware 叠在 vLLM / SGLang 之上，只要求 agent 侧传入 `program_id` 和 termination signal。

## 关键实验/定理

### 结果 1：高并发 serving 吞吐

- 设置：OpenHands、mini-SWEAgent、ToolOrchestra、ScienceAgentBench 等 agent workflow；GLM-4.6 355B、Qwen3 235B、Qwen3-8B；GPU 集群与工具环境分离部署。
- Baseline：vLLM request-level serving、Continuum multi-turn serving。
- 指标：steps per minute；一个 step 包含 reasoning 与 acting。
- 结果：ThunderAgent 在 serving 中相对 vLLM 达到 $1.48\times$ 到 $3.58\times$，相对 Continuum 达到 $1.17\times$ 到 $3.31\times$。
- 解读：在工具时长可预测时，ThunderAgent 能保持接近最优 KV hit rate；在工具时长随机或长尾时，它会主动牺牲部分 cache hit，减少长时间 acting program 占用 HBM。

### 结果 2：RL rollout 吞吐

- 设置：GLM-4.6 rollout，$N=144$，两台 $8\times$H100 节点。
- Baseline：vLLM + SGLang Gateway。
- 指标：steps per minute。
- 结果：

| Workflow | Serving system | Throughput | Speedup |
| --- | --- | ---: | ---: |
| mini-SWEAgent | vLLM + Gateway | 375.4 | 1.00x |
| mini-SWEAgent | ThunderAgent | 671.8 | 1.79x |
| OpenHands | vLLM + Gateway | 69.1 | 1.00x |
| OpenHands | ThunderAgent | 270.8 | 3.92x |

- 解读：agentic RL 的 rollout 阶段长期占据 wall-clock；ThunderAgent 对 rollout 有直接价值，因为它提升的是完成 trajectory step 的 sustained throughput。

### 结果 3：组件消融与可扩展性

- 设置：GLM-4.5-fp8 + mini-SWEAgent，H100 节点，高并发 program。
- Baseline：vanilla vLLM。
- 指标：steps per minute。
- 结果：

| 组件 | Throughput |
| --- | ---: |
| vLLM baseline | 375 |
| + local program-aware scheduling | 602 |
| + global waiting queue (ThunderAgent) | 672 |

- 解读：本地 program-aware scheduling 贡献最大，说明 KV thrashing 与 acting/reasoning 状态判断是主要收益来源；global waiting queue 进一步处理多节点 memory imbalance。

## 证据链强度评估

### 强证据

- 论文直接测了实际 agent workflow，证据强于只使用 synthetic prompt length distribution。
- serving 与 RL rollout 两类场景都给出端到端 steps/min 结果。
- 消融把 local program-aware scheduling 与 global waiting queue 的贡献拆开，说明收益来自多个调度组件。
- 开源仓库、SkyRL 集成和 NVIDIA Dynamo 集成增强了系统可复现性和生态价值。

### 中等强度证据

- 时间衰减函数的指数 / 几何形式有理论推导，但工具时长的 memoryless 假设在真实工具中只是一种近似。
- shortest-first eviction 的平方成本推导适合作为调度启发；实际 prefill kernel、chunking、paged KV、batch shape 和网络拓扑会改变常数项。
- tool resource manager 带来约 10% latency 改善和 $4.2\times$ disk memory savings，但这部分强依赖工具环境的初始化和清理策略。

### 需要谨慎的推论

- ThunderAgent 提升 throughput；单个用户请求的即时响应体验仍需用 tail latency / fairness 指标单独评估。
- 低 KV hit rate 在某些随机工具 workload 下仍可能对应更高吞吐，因为它减少了 stale acting program 占用 HBM；因此 cache hit rate 需要和 completed steps、recompute tokens、HBM occupancy 一起判断。
- 若某个 online agent service 的工具调用非常短、上下文很小、并发较低，program-aware scheduling 的收益会下降。

## 本地讨论补充

### 1. 讨论收敛点

- 对 online agentic server，若请求会经历多轮 tool use、prefill 和 decode，Memory / Compute 设备亲和有价值，但亲和对象应从单个 request 提升到 program / trajectory。
- 严格把请求发回原始 instance 可以保 KV，但在 session 长度、工具等待时间和活跃模式高度异质时，会降低调度自由度，使部分节点积累更多 KV footprint 或突发恢复请求。若 workload 足够均匀、session 数很大且分配依据包含真实 KV footprint，这种 imbalance 会减弱。
- ThunderAgent 的时间衰减属于无预测器的保留优先级老化策略，应避免把它解读为历史成本追责或严格的剩余工具时间预测器。更精确的策略应比较继续保留 KV 的未来 recompute saving 与继续占用 HBM 的未来机会成本。
- 轻量级预测器可以作为补充特征。在长尾、不可预测工具时长下，elapsed-time decay 是鲁棒默认策略；在近确定性工具时长下，应使用工具类型、历史统计或剩余时间预测替代固定指数衰减。

### 2. 修正后的理解

- agentic inference 的关键状态包括 prompt tokens、tool phase、tool environment、backend placement 和 program termination。
- KV cache 复用和设备亲和需要和 HBM occupancy 一起优化；缓存命中率是中间指标，完成 workflow step 的吞吐是主指标。
- RL rollout 场景下，program-aware serving 还能影响 policy lag，因为 rollout throughput 决定采样速度和异步训练中的数据 staleness。

### 3. 后续复验指标

- per-program token count、phase、tool duration、pause / restore 次数、re-prefill token 数。
- 每个 backend 的 KV occupancy、active reasoning program 数、acting program cached footprint。
- steps/min、program completion time、P50/P90/P99 per-step latency、tool environment init / teardown time。
- paused program 是否迁移、迁移后的 re-prefill cost、全局队列等待时间。
- rollout/trainer logprob consistency 与 batch nondeterminism 指标，特别是在 RL 训练闭环中。

## 主要启发

- agent server 的 API 最少也要有 `program_id` / `trajectory_id`、phase 或 tool-use state，以及 termination signal；这些信号是 runtime 调度质量的基础。
- 对多轮 tool-use agent，调度器应把 “保 KV” 当作带成本的动态决策。
- 在异构或多节点部署里，workflow-level global queue 可能比 session stickiness 更稳，尤其当 context length 和 tool wait time 长尾明显。
- tool resource manager 和 GPU KV scheduler 需要共享 lifecycle；否则 GPU 已释放但 Docker / port / disk 未释放，长跑 rollout 仍会失败。

## 局限

1. 论文主要以 throughput 为中心，用户交互型场景中的 tail latency / fairness 需要额外策略。
2. 时间衰减函数依赖不可预测工具时长假设；对于高度可预测的工具，如固定截图周期，线性或更任务特定的 decay 可能更合适。
3. 全局队列通过允许 paused program 跨节点恢复降低 imbalance，但会带来 re-prefill 和迁移决策复杂度；低并发或极长上下文场景需要重新评估。
4. 工具环境管理收益依赖具体 orchestrator、镜像大小、文件系统和 sandbox 生命周期；不同生产环境可能需要单独压测。
5. 论文没有完整给出统计置信区间和 baseline 调参细节，复现时应固定版本、容器配置和 workload seed。
